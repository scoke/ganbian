# ganbian

项目初始化。

## 技术方案说明

竿边（ganbian）面向个人垂钓记录：减少出钓前的重复配置，按竿提醒换饵，可靠保存现场记录，并回看不同环境与配置下的结果；后续考虑多用户与多端使用。

> **当前状态：方案评审，尚未实现。** 仓库目前仅有 README，没有应用代码、依赖配置或可执行脚本。下文整理 v0.1 评审方案（2026-10-29），区分已确认方向、候选实现与待确认事项；不代表应用已开发、部署或通过验收。

### 1. 产品范围与业务规则

核心流程：选择钓点 → 到点观察 → 本场安排与饵料 → 批量配置 → 逐竿微调 → 校验开始 → 现场记录与提醒 → 手动结束 → 历史与统计。

已确认的核心规则：

- 开始前可记录走水与实测水温；气温不能代替水温，未记录值不能当作零。
- 顶部支持统一配置，每支竿仍可单独调整；每竿的饵料、钓组、换饵间隔均必填。
- 换饵间隔选项为 1、1.5、2、3、4 小时；饵料常用间隔只帮助填入，最终执行用户选择的值。
- 钓组分为三叉钩＋浮球、翻板钩·钢丝可定型款、翻板钩·普通尼龙线款、反底钓浮钓组；最后一项标准名称仍待核对。
- 准备过程不计入垂钓时长；调整间隔不重置上次换饵时间，单竿换饵不影响其他竿。
- 环境与历史建议不能自动覆盖用户设置；提醒响一次即可，通知送达不等于用户已经换饵。
- 潮汐入口采用可跨日拖动的统一时间轴；走水与潮汐阶段独立记录，不由高潮或低潮推断走水。
- 多用户只能访问各自数据，权限必须由服务端校验。

本期不做渔获预测模型、社交、支付或同一场次的多人协作编辑；微信小程序另行评估。

### 2. 总体架构与平台边界

已确认采用“共享应用＋平台适配”的路线，后端仅使用 Cloudflare，本地开发默认使用本地数据库。以下为候选实现，具体依赖和数据选型仍需验证、定稿。

| 层次 | 候选方案 | 职责与限制 |
| --- | --- | --- |
| 手机与 Web | Expo / React Native | 共享应用主体、类型、规则与通用 UI；不同平台分别构建 |
| Mac 桌面 | Electron 加载导出的 Web 构建 | 主进程管理窗口、桌面数据库与系统能力；不复制业务页面 |
| 共享业务 | 纯 TypeScript 领域逻辑与契约 | 计时、校验、统计规则不依赖 UI 或平台框架 |
| 服务端 | Cloudflare Workers，建议 TypeScript | 认证、归属校验、业务用例与同步；不是完整 Node.js 运行时 |
| 云端数据库 | D1（待确认） | 个人目录、场次、事件与同步元数据；不是远程 MySQL 服务 |
| 本地存储 | 手机 SQLite、Web IndexedDB、桌面主进程 SQLite | 独立保存离线数据与待同步队列，不与 D1 自动同步 |
| 照片存储 | 需要云备份时引入 R2（待确认） | 与业务记录分开管理；照片不塞入 D1 |

候选请求链路：客户端 HTTPS → Worker 验证身份与资源归属 → 业务用例 → D1。Cloudflare 管理 Token 不下发客户端。

通知、存储、照片文件、定位、分享导出分别使用窄接口，显式报告权限和能力状态。Electron 通过受限 preload/IPC 暴露能力，不向页面开放完整 Node.js、任意 SQL 或文件系统访问。

微信小程序未来可复用纯业务逻辑与 HTTP 协议，但渲染、登录、通知和存储需独立适配；不能默认 Expo 直接输出小程序。

### 3. 领域模型与数据约束（建议）

| 实体 | 主要内容 |
| --- | --- |
| User / Identity | 内部用户 ID、状态，以及登录提供方与外部身份映射 |
| Bait / Spot | 个人饵料目录、常用间隔、归档状态；钓点名称与可选坐标 |
| Session | 账号归属、起止时间、状态、钓点及起点环境快照 |
| Rod | 所属场次、竿序号、饵与钓组快照、当前间隔 |
| Event | 换饵、间隔调整、鱼获、环境观察、更正或撤销事件 |
| Attachment | 文件归属、关联记录、上传状态 |

- 使用稳定 ID、版本及创建/更新时间；删除标记参与同步，避免旧设备使已删除记录复活。
- 时间点保存 UTC，展示使用场次时区；间隔统一使用整数分钟或秒，单位需在契约中定稿，不能将 1.5 小时截成 1 小时。
- 目录关联与历史快照并存，重命名或归档饵料不改写过去；未称重使用 `null` 而非 0。
- 环境记录区分观察时间、走水、实测水温、气温、来源、位置及接口更新时间；更新环境追加时间线，不覆盖起点。
- 个人数据带账号归属，事件同时校验父场次；索引覆盖账号、时间与场次等查询条件。
- 客户端数据库与 D1 可共享领域模型，但迁移脚本不假定相同；迁移进入版本控制，数据库和真实用户数据不入库。

### 4. 离线保存与同步（建议）

1. 业务修改与 outbox 操作在同一本地事务保存；操作包含 `operation_id`、`entity_id`、`base_version`、载荷与账号归属。本地保存成功后才提示已记录。
2. 服务端从验证后的身份确定账号，以“用户＋操作 ID”去重；重复上传返回同一结果，不能产生重复换饵或鱼获事件。
3. 可编辑对象使用原子条件更新检查版本。新增事实优先追加，更正或撤销关联原事件；并发修改目录或备注时保留双方内容并报告冲突，不静默覆盖。
4. 按账号使用单调变更游标下载增量与删除标记；本地事务同时应用数据和保存游标，中断可重试。客户端时间不作为全局同步顺序的唯一依据。
5. 本地数据与队列按账号隔离，退出时停止原账号任务；游客导入是否支持及其归属确认流程仍待定。

云端不可用时保留本地记录与 outbox，展示待同步或失败状态，不因上传失败清空记录。D1 与本地数据库的绑定切换不是同步机制；KV 不用于替代需要唯一约束或并发控制的业务主存储。

### 5. 计时与通知可靠性

计时以持久化的绝对时间为准：`到期时间 = 上次换饵时间 + 当前间隔`。例如上次换饵 10:00，10:30 将间隔改为 1.5 小时，到期应为 11:30，而不是从修改时刻重新计算。

候选实现要求：

- 重新打开按持久化时间恢复，倒计时不从完整间隔重启，也不每秒写库或请求云端。
- 通知 ID 映射场次与竿；变更后取消旧排程并建立新排程，场次结束取消该场未来提醒。预计结束时只提醒，不自动结束场次。
- 本地保存与系统通知并非同一事务；调度失败保留可恢复状态，不能显示排程成功。重启或唤醒时校对业务状态与系统排程。
- 建议指定提醒设备，其他设备首版只读进行中的计时配置；提醒设备离线时不能承诺远程修改已取消通知，此规则仍待确认。

| 平台 | 候选提醒能力与边界 |
| --- | --- |
| iOS / Android | 使用原生本地通知，真机验证权限、锁屏、断网、重启及系统省电限制；不承诺绕过系统策略 |
| Web | 首版仅页面提醒，不承诺关闭浏览器后定时；Web Push 另作联网能力评估 |
| Mac | 首版桌面驻留调度；完全退出或休眠不承诺准点，唤醒后校对到期状态 |

首次投饵基准、缩短间隔后已到期是否即时响一次、暂停含义及退出账号后的通知责任均待定，不由本说明隐性定稿。

### 6. 环境数据、安全与成本

- 手工观察与离线记录不依赖天气、潮汐接口成功；模拟、缓存、实时数据分别标识来源、位置和更新时间。
- Open-Meteo 为天气试选方向，潮汐服务仍待核对授权、站点与适用性；附近海洋站点不能冒充具体河道水位，真实数据仅展示覆盖范围。
- 历史常用间隔不等于最佳间隔；样本不足时不输出精确推荐，统计展示样本量，不推断未经验证的因果关系。走水筛选口径仍待定。
- 登录提供方尚未选择；服务端验证令牌与每次读写归属，附件和导出同样受控，客户端传入的用户 ID 不作为授权依据。
- 凭据按平台安全存储，不写入仓库或日志；local、staging、production 使用独立数据和密钥。
- 采用分页、增量同步和必要索引，按 Workers 请求/CPU、D1 行读写/容量、照片操作与认证服务估算费用。免费额度不是服务承诺，不自动升级付费方案。
- 域名、邮件/短信、环境接口、签名与发行渠道可能另有成本；上线前重新核对官方额度、网络可用性与超限行为，并验证备份恢复。

### 7. 工程组织与开发环境（建议）

建议采用 monorepo，先建立有真实调用者的模块，不为目录完整创建空包：

| 拟议路径 | 职责 |
| --- | --- |
| `apps/app` | Expo 路由、业务 features、布局与应用初始化 |
| `apps/desktop` | Electron main、preload、IPC 与生命周期 |
| `apps/api` | Workers 入口、认证、路由、D1 仓储及迁移 |
| `packages/fishing-core` | 纯领域模型、计时、校验和统计函数 |
| `packages/contracts` | HTTP/同步契约、运行时校验与错误码 |
| `packages/ui` | 通用组件与设计 token；不放竿卡等业务组件 |
| `packages/platform` | 通知、文件、设备能力接口与各端适配 |
| `packages/data` | 客户端仓储、本地适配、outbox 与同步驱动 |
| `packages/tooling` | 共享检查、类型与测试配置 |

依赖方向为应用引用共享包；纯业务不依赖平台，客户端不导入服务端密钥或数据库管理模块。

Mac 开发环境拟使用 Git、与 Expo SDK 兼容的 Node.js LTS、统一包管理器及锁文件。后端由 Wrangler 提供本地 Workers/D1，不另建 Node 服务器、MySQL 或必需的 Docker 环境；Web 和 Electron 共用应用构建。iPhone 使用 Xcode 与原生 development build；Android 使用对应 SDK/JDK 和开发构建。真机访问 Mac 局域网地址，而非手机的 `localhost`。

**目前没有安装或运行命令可供执行。** 待工程骨架建立后，再补充经验证的依赖安装、本地迁移、各端启动与构建步骤；开发命令不得隐式操作生产。

### 8. 实施阶段与验收

建议依次推进：S1 需求基线 → S2 工程骨架 → S3 手机通知/存储能力验证 → S4 业务迁移 → S5 账号同步 → S6 多端与环境 → S7 候选发布 → S8 现场试用。不承诺未经估算的工期，阶段列出不表示已完成。

关键验证范围：

- 纯规则测试：必填校验、批量与单竿配置、1.5 小时精度、换饵基准、统计缺失值与零时长。
- 存储/同步测试：离线重开、重复上传、原子版本冲突、删除不复活、账号切换及跨账号接口访问。
- 通知真机测试：前后台、锁屏、断网、权限拒绝、取消重排、结束与重启恢复；浏览器模拟不能替代原生验证。
- 发布测试：目标安装包、数据库升级、未同步数据保留、备份恢复、环境隔离与实际用量。

数据丢失、跨账号访问、必填绕过、错误重置计时、已结束仍提醒、模拟数据冒充真实和升级损坏数据均阻断发布。当前尚未执行这些应用验收。

### 9. 待确认决策

- **D03—D06：** 同时活跃场次、首次投饵基准、改短后已到期的提醒、暂停语义。
- **D07—D10：** 环境输入边界与站点适用性、输入/照片限制、推荐样本与走水统计口径、历史更正及删除恢复范围。
- **D11—D12：** 登录方式、游客导入与账号恢复，以及退出账号和多设备提醒责任。
- **D13—D14：** D1/R2 数据选型与引入时机、费用边界、首发平台与分发渠道。
